# WebGPU renderer

WebGPU is the preferred backend. The user's mandatory default-Chrome support now supersedes the earlier WebGPU-only requirement. WebGL2 automatically renders the same world when WebGPU is absent, insecure, blocklisted or fails during startup. No player-facing backend choice or experimental flag is required.

Reference analysis for WP-S001-003-001: [PlayCanvas's device creation reference](https://api.playcanvas.com/engine/functions/createGraphicsDevice.html) supports ordered WebGPU/WebGL2 selection. The supplied Chrome 154 / Android 16 report for Samsung SM-A556E lists both Xclipse 530 Dawn adapters as blocklisted while WebGL is hardware accelerated. [Chrome's troubleshooting reference](https://developer.chrome.com/docs/web-platform/webgpu/troubleshooting-tips) explains that blocklisting can cause a null adapter. The application cannot change browser policy. WebGPU compatibility mode would not bypass a blocklisted adapter, and engine-wide support remains an [open PlayCanvas issue](https://github.com/playcanvas/engine/issues/7903).

`src/renderer.ts` constructs `WebgpuGraphicsDevice` directly and awaits `initWebGpu`. On failure, the policy destroys the failed device before constructing `WebglGraphicsDevice` on a fresh canvas; a canvas already bound to WebGPU cannot switch context types. Controls bind to the actual device canvas. Built-in PlayCanvas materials provide WGSL and GLSL, so both backends render terrain, structures, foliage and resident billboards without external translators. World authority and fantasy-time simulation remain identical.

Startup checks secure context and the WebGPU API, then attempts WebGPU before WebGL2. The backend label reports the actual renderer; telemetry retains `fallbackReason` for diagnosis. Only failure of both backends displays the error panel and **Retry rendering**. Old renderer query parameters do not override automatic selection.

The renderer exposes requested backend, actual backend, phase and failure reason through `window.advisorRenderer` and `window.advisorWorld.renderer`. Device loss pauses frame uploads and displays recovery controls; PlayCanvas's device-restored event resumes rendering and the deterministic clock catches up.

## Verification

WP-S001-003-001: 16 functional tests and the production build pass. Fresh [blocked-adapter phone screenshot](evidence/default-chrome-fallback-phone.png) was opened and inspected: **8/10** for the existing prototype. Terrain, roofs, trees, residents and map controls render with the WebGL2 label; no error overlay, clipping or control overlap. The large atlas panel occupies much of the narrow screen, and art remains low-poly. Physical Samsung performance is not yet verified. Real WebGPU CI checks remain mandatory alongside the fallback suite.

`npm test` checks WebGPU preference, fallback ordering, cleanup, missing API, cancellation and combined failures. Browser tests simulate missing WebGPU, a null adapter, device creation failure, failure after canvas binding and unavailable WebGL2. Phone-sized screenshots, zoom and cell inspection verify the fallback world. CI also runs `npm run test:webgpu`, which requires actual WebGPU rendering and cannot pass on WebGL2. Physical Samsung testing remains a user-device check; desktop phone-size tests do not certify its GPU performance.

The software-test launch options follow [Chromium's SwiftShader WebGPU test configuration](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/third_party/blink/web_tests/FlagSpecificConfig). These flags apply only to the test browser; the game does not change browser settings or require them on supported hardware.

Fallback verification uses `npx playwright test --config playwright.fallback.config.js`, with only software WebGL test flags. The Vulkan compositor configuration required for the WebGPU suite hung the first fallback CI browser; the two driver configurations are kept separate. Neither changes production browser settings.

Historical WebGPU-only verification: the build and 14 functional checks passed. The Linux runner rendered WebGPU village and detail without GPU/shader errors in [run 37605770976](https://github.com/sgoxel/The_Advisor_Game/actions/runs/37605770976). This earlier version had no fallback; the current policy above supersedes it.

The initial CI failures came from [headless canvas presentation without a GPU-enabled Vulkan compositor and X display](https://github.com/visgl/luma.gl/issues/2874). Acquiring the swapchain texture dropped the native device and made later staging-buffer allocations fail. CI now runs with Xvfb, GPU-enabled headless rendering and Vulkan/SwiftShader compositing. Temporary native-device diagnostics were removed. Software WebGPU rendering is verified; hardware/mobile frame-rate benchmarking remains future work.

The finalized implementation `be2566e` [passed WebGPU rendering and deployed successfully](https://github.com/sgoxel/The_Advisor_Game/actions/runs/37606605638). The [village](evidence/webgpu-village.png) and [zoomed detail](evidence/webgpu-detail.png) screenshots were opened and inspected. Prototype visual score: **8/10**. Terrain, buildings, trees, bridge and resident artwork render correctly; the shortened-window map panel no longer overlaps the footer or status bar. Remaining art limitations are the same low-poly foundation noted in the original verification report.
